1. What NEXUS is and how to work in it

  • A configurable higher-education platform (Obsidian Labs). SIT Mysuru is a proposed pilot; all data is fictional until institutional access is authorized.
  • Stack: Next.js 16 (App Router, server components, server actions), React 19, TypeScript, PostgreSQL via pg, Zod 4, Better Auth, Playwright, node:test through tsx. Node 24 and npm.
  • Read AGENTS.md first. It is binding: tenant-scoped SQL, server-side session and workspace resolution, write rules in domain services, validated input, private downloads, transactional state changes, metadata-only audit events, immutable applied migrations, no real records, no credentials in git.
  • Registry of truth: docs/NEXUS_MASTER_FEATURE_REGISTRY.md (480 permanent IDs). Every change traces to IDs; status "Tested" applies only to the scope described. A status with a parenthesised scope note counts as partial.
  • Evidence: tests carry // covers: ID, ID on line 1. scripts/record-test-run.py writes docs/evidence/test-run.json; scripts/traceability.py regenerates the matrix. A row is "functionally tested" only if every linked test file passed in that recorded run.

2. Architecture conventions (follow these exactly)

ConcernRule as implemented
Scopelib/scope.ts: scope(institution, role) resolves the session and an active membership server-side; returns {institution, account, role}. Pages call it first; unknown workspace → 404.
ReadsEvery read model re-checks the caller's active membership/roster in SQL and returns []/null for the wrong role or tenant. Keys are composite (institution_id, id); always join on both. Fictional tenants reuse UUIDs, so test isolation by content, not id.
WritesDomain function in lib/*.ts: Zod parse → transaction() → lock the actor's membership (FOR SHARE) → lock the record → state check → write → audit(client, scope, entity, action, revision?, subject?). Throw WorkflowError for user-facing refusals.
ActionsServer actions in app/actions/*.ts only translate form data and map errors; no business rules. Forms use <ActionForm> (app/forms.tsx) with an operation field.
Locks & grantsThe runtime role nexus_app has column-level grants. FOR UPDATE/SHARE needs UPDATE privilege on that table — two bugs this week came from locking tables without it. Add grants in the migration that creates the table.
AutomationTransactional outbox: an audit_event insert enqueues job rows per automation_rule. Handlers in lib/automation.ts re-read state and return {notified}/{skip}/{defer}. Worker role nexus_worker cannot insert audit events. Notifications are re-checked at read time (notifications() visibility CASE — add a branch for any new kind).
SQL hygieneNever reuse an outer alias inside a subquery that references the outer row (an alias shadowing bug made an HOD check always true). Table names interpolated only from whitelists.
UIServer components; tokens from the Design Bible (app/styles.css, CSS modules per area). Every region has a heading via aria-labelledby; avoid region/heading names that are substrings of existing labels used by tests (two collisions this week). Check 390 px and 1280 px for horizontal overflow.

7. Definition of done for any change

  1. Domain service with Zod validation, membership re-check in SQL, transaction, audit event; grants in the migration.
  2. Integration test in tests/*.test.ts proving the positive path and denials: wrong role, other section, other tenant (by content), stale state, double decision.
  3. Browser test for the main path at 390 px without overflow; screenshot copied to docs/evidence/<area>-<date>/ before the tutor run clears test-results.
  4. Registry row status and evidence updated; authority note in the dependencies doc when authority changes; ledger entry with observed counts.
  5. Fresh-DB CI order green; record-test-run.py + traceability.py regenerated and committed with the code commit hash.

8. Scoring model used for "progress out of 100"

An informal weighting reported to the founder: registry coverage (full + half of partial, of 480), Design Bible screens built (~30 boards), automation engine maturity, the 90% effort-reduction goal proven with measured baselines, and production readiness (hosted, restored, monitored). The last two carry heavy weight and are 0 because they need real hosting and real participants. Code alone can raise the score into the high 30s; 40 and beyond need the founder gates below.
